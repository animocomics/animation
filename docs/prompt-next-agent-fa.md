# پرامپت نهایی برای ایجنت بعدی — هدف: کایا مستقیم کار کند

این متن را کامل کپی کنید و به ایجنت جدید بدهید. هیچ توضیح اضافه‌ای لازم نیست.

---

## پرامپت (از اینجا تا آخر کپی شود)

سلام. یک پروژهٔ Next.js (سیستم تصحیح برگهٔ امتحان) روی هاست Plesk در ایران دارم. درخواست‌های هوش مصنوعی به سرویس ایرانی **کایا** (`https://kayaai.ir/api`) می‌رود. مشکل: **از این هاست به کایا وصل نمی‌شود.** باید **مستقیم** کار کند. راه‌حل موقت، relay، تونل، V2Ray، پروکسی، worker روی GitHub یا هر دور زدنی **ممنوع** است. همان درخواستی که برنامه می‌فرستد باید به کایا برسد و جواب بگیرد.

**این کار باید انجام شود.** اگر شواهد نشان داد از داخل کد غیرممکن است، باید با دلیل مشخص و قابل‌آزمون بگویی کدام لایه بسته است و چه کسی (هاستینگ یا کایا) باید آن را باز کند — نه اینکه بی‌صدا رها کنی و نه اینکه نسخه بسازی.

### ۱) واقعیت‌های قطعی — اینها را دوباره آزمایش نکن

| # | واقعیت | شاهد |
|---|---|---|
| ۱ | کایا سالم است | از IP آمریکا `GET https://kayaai.ir/api/chat/completions` → **HTTP 200** با فهرست مدل‌ها |
| ۲ | URL و قرارداد درست است | همان GET، و `GET https://kayaai.ir/api/models` هم لیست می‌دهد |
| ۳ | شکست در لایهٔ TCP است | خروجی خود هاست: `tcp 443 213.176.6.243 (kayaai.ir) TIMEOUT (no answer) 8002ms` |
| ۴ | کد برنامه در این مرحله اجرا نمی‌شود | سوکت باز نمی‌شود؛ هیچ کلید/مدل/فایلی فرستاده نمی‌شود |
| ۵ | DNS و فایروال محلی پاک است | `resolv.conf` = `185.192.112.100, 185.192.113.100`؛ بدون TUN، بدون پروسهٔ VPN، بدون پروکسی، بدون قاعدهٔ redirect |
| ۶ | فیلتر مخصوص مقصد است | از همان هاست در همان دقیقه: `api.github.com` و npm registry سبز، کایا timeout |
| ۷ | IP خروجی با IP سرور یکی نیست | `api.ipify.org` → `51.81.168.118` (**OVH آمریکا**)؛ `icanhazip` گاهی `185.192.112.49` (ایران) |

| ۹ | آدرس ایرانی روی کارت شبکهٔ سرور نیست | فقط یک آدرس غیرلوکال دارد؛ آن هم آدرس عمومی ایران نیست |

### ۲) محدودیت‌هایی که اگر رعایت نشوند کار خراب می‌شود

**الف) سقف درخواست، برای کل سرور است — نه برای هر API.**
قاعدهٔ میزبان این است: **بیش از ۲۰۰ درخواست در ۲۰ دقیقه به هر مقصدی ⇒ خروجی کل سرویس مسدود می‌شود.** یک بار همین اتفاق افتاد: یک worker در حلقه ۳۶۱۲ درخواست فرستاد و کل خروجی سرور از دست رفت.

پس:
- **هیچ worker، حلقه، watcher، یا تست خودکار نساز** که خودش درخواست بفرستد.
- هر درخواست خروجی (همهٔ مقصدها با هم، در همهٔ پروسه‌ها) باید از یک سقف مشترک رد شود. این الان در `lib/server/outbound-window.ts` هست: فایل روی دیسک با قفل، پیش‌فرض **۱۲۰** در ۲۰ دقیقه (۸۰ خانه برای بقیهٔ ترافیک سایت).
- سقف را **بالا نبر**. اگر تستی لازم است، از `NOMREH_OUTBOUND_WINDOW_LIMIT` استفاده کن — که فقط `npm test` آن را می‌گذارد.
- هنگام دیباگ، درخواست تکراری نزن. یک درخواست می‌تواند ۴ لایه را همزمان نشان دهد.

**ب) محیط اجرا:**
- کاربر **shell ندارد**. فقط کنسول `npm` در Plesk که **همه را با `npm` پیشوند می‌کند**؛ یعنی فقط `npm run <script>` کار می‌کند. `node -e ...` کار نمی‌کند (`Unknown command: "node"`).
- Node کنسول **17** است: بدون `fetch`، بدون `?.`، بدون `??=`، بدون `structuredClone`، بدون `AbortSignal.timeout`. اگر Node 22 لازم داشتی، از `scripts/lib/plesk-node-delegate.cjs` استفاده کن (خودش را روی Node 22 محلی دوباره اجرا می‌کند).
- هیچ نصب گلوبال، هیچ `sudo`، هیچ `iptables` (root ندارد).
- همهٔ اطلاعات ورود و کلیدها در **secret** هستند (`NOMREH_SECRET_KEY` / `data/.provider-secret` / `.env.local`) — **هیچ کلیدی را چاپ نکن، در لاگ ننویس، در فایل نصبی نگذار، در پاسخ برنگردان.** برای تست کلید واقعی، از `lib/server/secret-crypto.ts` استفاده کن.

**ج) رفتار محصول:**
- **هرگز مدل را خودکار عوض نکن.** مدلی که ادمین انتخاب کرده باید همان باشد؛ حتی یک بار.
- **خطاهای پنل معلم هیچ جزئیات فنی نداشته باشد** — نه نام مدل، نه نام سرویس‌دهنده، نه کد HTTP.
- هرگز نگو «درست شد» مگر خودت خروجی موفق را دیده باشی. اگر تأیید نشده، صریح بگو «تأیید نشده».
- تغییر جراحی و با پشتیبان. کد موجود را نشکن. تست `npm test` و `npm run build` باید سبز بماند.

**د) سبک کار:**
- پاسخ‌ها **فارسی**.
- پاسخ **کوتاه**. کاربر از حجم توضیح و نسخه‌های پشت‌سرهم کلافه شده است.
- **فایل zip جدید نفرست** مگر خودش بخواهد. اول تشخیص، بعد یک بستهٔ نهایی.
- برای هر تغییر کوچک، نسخهٔ جدید نساز.

### ۴) کارهایی که قبلاً وقت هدر داد — تکرار نکن

- تست دوبارهٔ DNS/TLS/TCP «شاید این بار» — ۶ ساعت نتیجه ثابت بوده.
- `traceroute -T` (اجازه ندارد) و `iptables` (root ندارد).
- فرض «کایا IP خارجی را تحریم کرده» — **رد شد**؛ کایا به IP آمریکا ۲۰۰ می‌دهد. مشکل این است که ما از IP خارجی بیرون می‌رویم در حالی که سرور در ایران است.
- فرض «همهٔ خروجی OVH است» — رد شد؛ بستگی به مقصد دارد.
- ساختن نگهبان/مانیتور — کاربر صریحاً نمی‌خواهد.
- ادعای «Gemini تحریم است» — **رد شد**؛ Gemini با کلید معتبر از IP آمریکا کار می‌کند (تحریم ایران به IP غیرایرانی کاری ندارد). ایران در فهرست کشورهای مجاز گوگل نیست، ولی از IP آمریکا سرویس جواب می‌دهد.

### ۵) کاری که باید بکنی، به ترتیب

**گام ۱ — پیدا کردن آدرسی که کایا قبول می‌کند (بدون حدس).**
از کاربر بخواه در `/admin` → «تشخیص شبکه» سه چیز را ببیند:
- `IP عمومی خروجی`
- `آدرس‌های روی این سرور`
- خروجی `npm run kaya:egress -- --test`

**گام ۲ — اگر آدرسی روی همان ماشین هست:** در فیلد «آدرس خروجی برای کایا» بگذار و با «آزمون واقعی کایا» تأیید کن. تا سبز نشد، چیزی نساز.

**گام ۳ — اگر آدرس ایرانی روی کارت شبکه نیست (حال فعلی):** این را صریح بگو: bind کردن آدرسی که روی ماشین نیست ممکن نیست (`EADDRNOTAVAIL`)، و **این تنها جایی است که کد نمی‌تواند کمکی کند.** دو راه مستقیم باقی است و انتخابش با کاربر است، نه تو:
- (الف) از هاستینگ بخواه آدرس ایرانی را secondary روی interface بگذارد (متن نامه در `docs/kaya-block-diagnosis-fa.md`).
- (ب) سرویس‌دهنده را عوض کن به یکی که از IP فعلی (آمریکا) جواب می‌دهد. **با شواهد، نه حدس:** کایا از IP آمریکا ۲۰۰ می‌دهد؛ Gemini هم با کلید معتبر از IP آمریکا کار می‌کند.

**گام ۴ — فقط وقتی مسیر باز شد:** بستهٔ نهایی با `npm test` و `npm run build` سبز، و بعد بگو کار می‌کند که خروجی موفق را دیده باشی.

### ۶) تعریف موفقیت

یک تصحیح واقعی روی هاست، با کایا، بدون هیچ واسطه، که خروجی موفقش دیده شده باشد. نه کمتر.
