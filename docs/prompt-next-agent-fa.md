# پرامپت نهایی برای ایجنت بعدی — هدف: کایا مستقیم کار کند

این متن را کامل کپی کنید و به ایجنت جدید بدهید. هیچ توضیح اضافه‌ای لازم نیست.

---

## پرامپت (از اینجا تا آخر کپی شود)

سلام. یک پروژهٔ Next.js (سیستم تصحیح برگهٔ امتحان) روی هاست Plesk در ایران دارم. درخواست‌های هوش مصنوعی به سرویس ایرانی **کایا** (`https://kayaai.ir/api`) می‌رود. مشکل: **از این هاست به کایا وصل نمی‌شود.** باید **مستقیم** کار کند. راه‌حل موقت، relay، تونل، V2Ray، پروکسی، worker روی GitHub یا هر دور زدنی **ممنوع** است. همان درخواستی که برنامه می‌فرستد باید به کایا برسد و جواب بگیرد.

**این کار باید انجام شود.** اگر شواهد نشان داد از داخل کد غیرممکن است، باید با دلیل مشخص و قابل‌آزمون بگویی کدام لایه بسته است و چه کسی (هاستینگ یا کایا) باید آن را باز کند — نه اینکه بی‌صدا رها کنی و نه اینکه نسخه بسازی.

> **این ریپو تازه است.** کد پروژهٔ قبلی اینجا نیست؛ فهرست فایل‌هایی که باید بیاوری در انتهای همین متن است (§۷). نصب فعلی روی هاست **v26** است و سالم بالا می‌آید.

### ۰) آخرین وضعیت تحویل (v29)

- **نسخهٔ فعلی: `nomreh-direct-v29.zip`** روی همین برنچ. هرگز نسخهٔ قدیمی‌تر را نصب نکن.
- **مسیر خواندن برگهٔ سؤال/کلید در v29 درست شد** — این سه عیب واقعی بود، نه گمانه:
  1. **ساختار پیش‌نویس بیش از حد سخت‌گیر بود.** اگر مدل یک فیلد را جا می‌گذاشت (بیشترین مورد: `rubric`) یا `maxScore` را رشته می‌فرستاد («2» یا «۲»)، **کل جواب دور ریخته می‌شد** در حالی که توکن‌ها خرج شده بودند و کاربر فقط «ساختار پیش‌نویس مدل کامل نیست» را می‌دید. حالا فیلدهای بی‌خطر عادی‌سازی می‌شوند؛ فقط چیزی که نباید حدس زده شود سخت می‌ماند (صورت سؤال خالی، نوع ناشناخته، نمرهٔ غیرعددی).
  2. **یک سؤال ناخوانا کل پیش‌نویس را دور می‌ریخت.** حالا سؤال‌های سالم می‌مانند و شمارهٔ سؤال‌های ردشده با دلیل در هشدار می‌آید (`salvageQuestionImport` + `normalizeImportedQuestions`). فقط وقتی هیچ سؤالی سالم نبود، خطای ۴۲۲ با نام همان سؤال‌ها برمی‌گردد.
  3. **`max_tokens: 32768` ثابت بود** و بعضی gatewayها آن را رد می‌کنند در حالی که تصویرها قبلاً حساب شده‌اند. حالا `NOMREH_MAX_OUTPUT_TOKENS` (پیش‌فرض ۳۲۷۶۸، مجاز ۱۰۲۴–۶۵۵۳۶) و اگر gateway یک پارامتر را با 400 رد کند، **یک‌بار** بدنهٔ ساده‌تر (`response_format`/`temperature`/`detail` بدون) دوباره فرستاده می‌شود — فقط برای همان حالت، نه برای ۴۰۱/۴۰۲/۴۲۹/۵xx که ارسال دوباره فقط پول دوباره خرج می‌کند.
- **آزمون زنده (نه فقط تست واحد):** با یک PDF واقعی ۷ صفحه‌ای از کاربر (`14011017po67622866.pdf`) روی بیلد production: هر ۷ صفحه به تصویر تبدیل شد (`images=7`)، مسیر import **HTTP 200** با سؤال‌های سالم، ذخیرهٔ پیش‌نویس **HTTP 200 / revision 6**، و بازخوانی همان سؤال‌ها از سرور. سالویج با سؤال عمداً خراب: ۲ سالم ماند، سؤال ۳ با هشدار حذف شد. رد پارامتر توسط gateway: ۴۰۰ → یک ارسال دوباره → ۲۰۰.
- **فهرست پسوندهای مجاز در خود UI نوشته شده** و از یک منبع واحد می‌آید (`lib/file-constraints.ts`): `ACCEPTED_FILE_EXTENSIONS`، `ACCEPTED_FILE_LABEL` = «JPG، JPEG، PNG، WebP، PDF». دکمهٔ «ورود CSV / Excel» در کلاس‌ها هم دیگر Excel را وعده نمی‌دهد؛ فقط CSV/TXT/TSV خوانده می‌شود.
- **هزینه: هیچ درخواست پرداختی دیگر خودکار تکرار نمی‌شود.** `NOMREH_PROVIDER_ATTEMPTS` پیش‌فرض **۱** است (سقف ۳). قبلاً هر شکست تا دو بار (۴۲۹/۵xx) و با تلاش دوبارهٔ بدنهٔ ساده تا سه بار همان تصویرها را دوباره می‌فرستاد؛ گیت‌وی ورودی را حتی وقتی ۵۰۳ برمی‌گرداند و پاسخی نمی‌سازد حساب می‌کند. تنها تلاش دوباره‌ای که مانده، برای ۴۰۰ «پارامتر پشتیبانی نمی‌شود» است، چون آن یکی جواب می‌دهد نه اینکه درخواستِ پرداخت‌شده را تکرار کند.
- **اندازهٔ واقعی هر ارسال:** PDF هفت‌صفحه‌ای کاربر بعد از تبدیل `1.7 MB` برای ۷ صفحه است (~۲۵۶KB هر صفحه، ~۲۰۰۰ توکن ورودی) — اندازه‌گیری شد، نه حدس.
- **آزمون‌ها: ۱۵۸/۱۵۸** (`npm test`) و `npx tsc --noEmit` پاک. هر عدد دیگری در این سند که کمتر است، قدیمی است.
- **مهم:** وقتی import شکست می‌خورد، دکمه را پشت‌سرهم نزن؛ هر تلاش، تصویر صفحه‌ها را دوباره به مدل می‌فرستد و دوباره هزینه می‌شود. پیام خطا حالا شمارهٔ همان سؤال و دلیلش را می‌گوید؛ فقط همان برگه را واضح‌تر بفرست.

### ۲) محدودیت‌هایی که اگر رعایت نشوند کار خراب می‌شود

**الف) سقف درخواست، برای کل سرور است — نه برای هر API.**
قاعدهٔ میزبان این است: **بیش از ۲۰۰ درخواست در ۲۰ دقیقه در مجموع — نه به تفکیک هر API — و کل خروجی سرور مسدود می‌شود.** یعنی سهم همهٔ مقصدها با هم و همهٔ پروسه‌های سرور با هم، بیست‌تا دویست‌تا. یک بار همین اتفاق افتاد: یک worker در حلقه ۳۶۱۲ درخواست فرستاد و خروجی کل سرور از دست رفت. پس «هر API جدا ۲۰۰ تا» غلط است؛ ۲۰۰ تا سهم کل ماشین است.

پس:
- **هیچ worker، حلقه، watcher، یا تست خودکار نساز** که خودش درخواست بفرستد.
- هر درخواست خروجی (همهٔ مقصدها با هم، در همهٔ پروسه‌ها) باید از یک سقف مشترک رد شود. این الان در `lib/server/outbound-window.ts` هست: فایل روی دیسک با قفل، پیش‌فرض **۱۲۰** در ۲۰ دقیقه (۸۰ خانه برای بقیهٔ ترافیک سایت).
- سقف را **بالا نبر**. اگر تستی لازم است، از `NOMREH_OUTBOUND_WINDOW_LIMIT` استفاده کن — که فقط `npm test` آن را می‌گذارد.
- هنگام دیباگ، درخواست تکراری نزن. یک درخواست می‌تواند ۴ لایه را همزمان نشان دهد.

**ب) محیط اجرا:**
- کاربر **shell ندارد**. فقط کنسول `npm` در Plesk که **همه را با `npm` پیشوند می‌کند**؛ یعنی فقط `npm run <script>` کار می‌کند. `node -e ...` کار نمی‌کند (`Unknown command: "node"`).
- Node کنسول **17** است: بدون `fetch`، بدون `?.`، بدون `??=`، بدون `structuredClone`، بدون `AbortSignal.timeout`. اگر Node 22 لازم داشتی، از `scripts/lib/plesk-node-delegate.cjs` استفاده کن (خودش را روی Node 22 محلی دوباره اجرا می‌کند).
- هیچ نصب گلوبال، هیچ `sudo`، هیچ `iptables` (root ندارد).
- همهٔ اطلاعات ورود و کلیدها در **secret** هستند (`NOMREH_SECRET_KEY` / `data/.provider-secret` / `.env.local`) — **هیچ کلیدی را چاپ نکن، در لاگ ننویس، در فایل نصبی نگذار، در پاسخ برنگردان.** برای تست کلید واقعی، از `lib/server/secret-crypto.ts` استفاده کن.

**ج) رفتار محصول:**
- **هرگز مدل را خودکار عوض نکن.** مدلی که ادمین انتخاب کرده باید همان باشد؛ حتی یک بار.
- **خطاهای پنل معلم هیچ جزئیات فنی نداشته باشد** — نه نام مدل، نه نام سرویس‌دهنده، نه کد HTTP.
- هرگز نگو «درست شد» مگر خودت خروجی موفق را دیده باشی. اگر تأیید نشده، صریح بگو «تأیید نشده».
- تغییر جراحی و با پشتیبان. کد موجود را نشکن. تست `npm test` و `npm run build` باید سبز بماند.

**د) سبک کار:**
- پاسخ‌ها **فارسی**.
- پاسخ **کوتاه**. کاربر از حجم توضیح و نسخه‌های پشت‌سرهم کلافه شده است.
- **فایل zip جدید نفرست** مگر خودش بخواهد. اول تشخیص، بعد یک بستهٔ نهایی.
- برای هر تغییر کوچک، نسخهٔ جدید نساز.

### ۳) کدی که هست و باید حفظ شود

| فایل | کار |
|---|---|
| `lib/server/outbound-window.ts` | سقف مشترک کل سرور (فایل + قفل) — **دست نزن، فقط استفاده کن** |
| `lib/server/provider-network.ts` | تنها خروجی درخواست‌ها: fetch مستقیم + سقف مشترک. هیچ dispatcher/پروکسی اینجا نیست |
| `lib/server/provider-rate-limit.ts` | گیت هر درخواست + circuit breaker |
| `lib/server/kaya-egress.ts` | انتخاب آدرس مبدأ سوکت برای کایا (تنها استثنا، و فقط چون bind کردن آدرس روی خود ماشین یک تونل نیست). **مهم:** `undici` گزینهٔ `connect.localAddress` را نادیده می‌گیرد؛ باید `buildConnector` را wrap کرد (تست‌شده) |
| `lib/server/kaya-egress-store.ts` + `app/api/admin/kaya-egress/route.ts` | ذخیره/خواندن آن آدرس + تشخیص «آدرس روی ماشین نیست» |
| `lib/server/kaya-probe-readings.ts` | تبدیل پاسخ کایا به جملهٔ لایه‌محور |
| `scripts/nomreh-kaya-test.cjs` | تست واقعی با کلید واقعی، ۳ درخواست، هرگز hang نمی‌کند |
| `scripts/nomreh-kaya-test-selftest.cjs` | ۱۱ بررسی بدون شبکه |
| `scripts/nomreh-kaya-egress-check.cjs` | فهرست آدرس‌های ماشین + کدام را کایا قبول می‌کند |
| `scripts/nomreh-kaya-measure.cjs` | اندازهٔ بدنهٔ درخواست در برابر سقف ۲۴MB |
| `docs/kaya-block-diagnosis-fa.md` | خلاصهٔ تشخیص + متن نامه به هاستینگ/کایا |

**دستورهایی که روی هاست کار می‌کنند — فقط در نسخهٔ v26 (همین بسته).** هر دستوری را با نام نسخه بگو؛ روی نسخه‌های قدیمی‌تر نصب‌شده این‌ها نیستند و خطای `Missing script` می‌دهند.

```
npm run kaya:selftest              # بدون شبکه، ۱۱ بررسی — همیشه بی‌خطر
npm run kaya:test                  # ۳ درخواست واقعی با کلید واقعی؛ هرگز hang نمی‌کند
npm run kaya:egress -- --test      # فهرست آدرس‌های ماشین + کدام را کایا قبول می‌کند
npm run kaya:measure               # اندازهٔ بدنهٔ درخواست در برابر سقف ۲۴MB
npm run diagnose                   # شبکهٔ هاست: DNS، آدرس‌ها، IP خروجی
```

`npm run kaya:check` یک‌بار اجرا می‌شود و تمام؛ `npm run kaya:watch` **نگهبان** است و کاربر آن را نمی‌خواهد — **اجرا نکن، نساز**.

**چطور بدون shell واقعیت را ببین.** کاربر فقط `/admin` را می‌بیند: تبِ «اتصال هوش مصنوعی». سه چیز در همان صفحه:
- دکمهٔ **«تشخیص شبکه»** → سطرهای `IP عمومی خروجی`، `آدرس‌های روی این سرور`، `resolv.conf`، `TUN`، `پروکسی`، `قاعدهٔ redirect` و در آخر یک جملهٔ نتیجه.
- فیلد **«آدرس خروجی برای کایا»** + چیپ‌های آدرس‌های موجود (کلیک = پر شدن فیلد).
- دکمهٔ **«آزمون واقعی کایا»** → سه لایه، هر کدام یک جملهٔ فارسی: کاتالوگ / متن / تصویر. این تنها آزمون معتبر است؛ هر جمله را عیناً بپرس و همان را تفسیر کن.

**تفسیر جمله‌های آزمون (این جدول را حفظ کن، دوباره نسنج):**

| جمله | معنی | کار بعدی |
|---|---|---|
| «کاتالوگ هم بی‌پاسخ ماند … لایهٔ شبکه» | سوکت باز نمی‌شود؛ هیچ کلیدی فرستاده نشد | فقط آدرس مبدأ / هاستینگ |
| «کلید پذیرفته نشد» | مسیر باز است، کلید مشکل دارد | `secret` را بررسی کن، کلید را چاپ نکن |
| «بدنه از سقف کایا بزرگ‌تر است» | مسیر و کلید سالم، حجم مشکل دارد | `npm run kaya:measure` |
| «سقف خروجی این پنجره پر شده است» | گیت خودمان جلوی درخواست را گرفت | ۲۰ دقیقه صبر، سقف را بالا نبر |
| «همهٔ لایه‌ها سالم‌اند» | مسیر، کلید، مدل، متن، تصویر | یک تصحیح واقعی بزن |

**چیزهایی که نباید دست بزنی:** `secret` و `data/` (کلید و رمز داخلشان است). همچنین بدان که **همهٔ ماژول‌های واسطه حذف شده‌اند**: Shecan، V2Ray، ماشین مجازی ویندوز، QEMU، VNC و بسته‌های `ws`/`novnc` دیگر وجود ندارند و تست `npm test` هم جلوی برگشتنشان را می‌گیرد. اگر مسیر مستقیم بسته بود، **دوباره‌ساختن هیچ‌کدام مجاز نیست** — جواب کد نیست، جواب هاستینگ یا سرویس‌دهنده است.

### ۴) کارهایی که قبلاً وقت هدر داد — تکرار نکن

- تست دوبارهٔ DNS/TLS/TCP «شاید این بار» — ۶ ساعت نتیجه ثابت بوده.
- `traceroute -T` (اجازه ندارد) و `iptables` (root ندارد).
- فرض «کایا IP خارجی را تحریم کرده» — **رد شد**؛ کایا به IP آمریکا ۲۰۰ می‌دهد. مشکل این است که ما از IP خارجی بیرون می‌رویم در حالی که سرور در ایران است.
- فرض «همهٔ خروجی OVH است» — رد شد؛ بستگی به مقصد دارد.
- ساختن نگهبان/مانیتور — کاربر صریحاً نمی‌خواهد.
- ادعای «Gemini تحریم است» — **رد شد**؛ Gemini با کلید معتبر از IP آمریکا کار می‌کند (تحریم ایران به IP غیرایرانی کاری ندارد). ایران در فهرست کشورهای مجاز گوگل نیست، ولی از IP آمریکا سرویس جواب می‌دهد.

### ۵) کاری که باید بکنی، به ترتیب

**گام ۰ — قبل از هر تغییری، دو دقیقه واقعیت را جمع کن.**
کاربر shell ندارد؛ پس تو هم نمی‌توانی تست کنی. هر چه لازم داری از او بخواه — **دقیق و کم**، نه ده سؤال. فقط این سه چیز:
1. عکس/متن خروجی دکمهٔ «تشخیص شبکه» (سطر `IP عمومی خروجی` و `آدرس‌های روی این سرور` مهم‌اند).
2. عکس/متن خروجی «آزمون واقعی کایا» (سه جمله).
3. اگر ممکن شد، خروجی `npm run kaya:egress -- --test` از کنسول Plesk (نسخهٔ v26).
تا این سه را نداری، هیچ کدی ننویس.

**گام ۱ — پیدا کردن آدرسی که کایا قبول می‌کند (بدون حدس).**
مسئلهٔ فعلی این است: سرور با آدرس OVH آمریکا (`51.81.168.118`) بیرون می‌رود و کایا آن را جواب نمی‌دهد، ولی هیچ آدرس ایرانی روی کارت شبکهٔ سرور نیست تا جای آن گذاشته شود. پس:
- اگر در «آدرس‌های روی این سرور» آدرس ایرانی دیدی (نه `169.254.*`، نه آدرس آمریکایی)، همان را بگذار و برو گام ۲.
- اگر ندیدی، برو گام ۳.

**گام ۲ — اگر آدرسی روی همان ماشین هست:** در فیلد «آدرس خروجی برای کایا» بگذار، ذخیره کن، و «آزمون واقعی کایا» را بزن. اگر کاتالوگ سبز شد، ادامه بده؛ تا سبز نشد، چیزی نساز.

**گام ۳ — اگر آدرس ایرانی روی کارت شبکه نیست (حال فعلی):** این را صریح و بی‌پرده بگو: bind کردن آدرسی که روی ماشین نیست ممکن نیست (`EADDRNOTAVAIL`)، و **این تنها جایی است که کد نمی‌تواند کمکی کند.** سه راه مستقیم باقی است و انتخابش با کاربر است، نه تو:
- (الف) از هاستینگ بخواه آدرس ایرانی را secondary روی interface بگذارد (متن آمادهٔ نامه در `docs/kaya-block-diagnosis-fa.md`). بعد از آن، همان گام ۲.
- (ب) اگر آدرس ایرانی هست و باز هم timeout می‌شود، یعنی فایروال خود کایا بازهٔ این هاستینگ را می‌بندد؛ آن را فقط کایا می‌تواند باز کند. این هم همان نامه، خطاب به کایا. مدرک برای فرستادن: `tcp 443 213.176.6.243 TIMEOUT` از همین هاست، در حالی که از IP آمریکا همان مسیر ۲۰۰ می‌دهد.
- (ج) سرویس‌دهنده را عوض کن به یکی که از IP فعلی (آمریکا) جواب می‌دهد. **با شواهد، نه حدس:** کایا از IP آمریکا ۲۰۰ می‌دهد؛ Gemini هم با کلید معتبر از IP آمریکا کار می‌کند.

**گام ۴ — فقط وقتی مسیر باز شد:** بستهٔ نهایی با `npm test` (۱۹۹/۱۹۹) و `npm run build` سبز، و بعد بگو کار می‌کند که خروجی موفق را دیده باشی.

### ۶) تعریف موفقیت

یک تصحیح واقعی روی هاست، با کایا، بدون هیچ واسطه: کاربر یک برگهٔ واقعی را در پنل معلم می‌فرستد، پاسخ می‌آید، و **همان خروجیِ تصحیح‌شده روی صفحه دیده می‌شود**. نه «آزمون سبز شد»، نه «تست پاس شد» — تصحیح واقعی. اگر این را ندیده‌ای، حق نداری بگویی درست شد.

## §۷ — کدی که باید از نسخهٔ v26 بیاوری

اگر این ریپو خالی است، این فایل‌ها را از بستهٔ نصب v26 (یا از ریپوی قبلی) بردار. همه با `node 17` سازگارند و هیچ وابستگی جدیدی لازم ندارند:
