# پرامپت آماده برای ایجنت بعدی — هدف: کار کردن مستقیم کایا

این متن را کامل کپی کنید و به ایجنت جدید بدهید. هیچ توضیح اضافه‌ای لازم نیست.

---

## پرامپت

سلام. یک پروژهٔ Next.js دارم (سیستم تصحیح برگهٔ امتحان) که روی هاست Plesk در ایران اجرا می‌شود. درخواست‌های هوش مصنوعی آن به سرویس ایرانی **کایا** (`https://kayaai.ir/api`) می‌رود. مشکل: **از این هاست به کایا وصل نمی‌شود.** می‌خواهم اتصال **مستقیم** درست شود. راه‌حل موقت، پروکسی، تونل، relay، یا دور زدن نمی‌خواهم. باید همان درخواستی که برنامه می‌فرستد، مستقیم به کایا برسد و جواب بگیرد.

### آنچه با شواهد قطعی است (اینها را دوباره آزمایش نکنید)

۱. **کایا سالم است.** از یک IP آمریکایی، `GET https://kayaai.ir/api/chat/completions` جواب **HTTP 200** با فهرست مدل‌ها می‌دهد. `GET https://kayaai.ir/` هم صفحهٔ خودش را برمی‌گرداند. پس سرویس کایا، URL، و قرارداد آن درست است.

۲. **شکست در لایهٔ TCP است، پیش از هر درخواستی.** خروجی واقعی از خود هاست:

```
== 1. transport
  system DNS    213.176.6.243
  tcp 443       213.176.6.243 (kayaai.ir) TIMEOUT (no answer) 8002ms
```

یعنی سوکت باز نمی‌شود. هیچ کلید، مدل یا فایلی فرستاده نمی‌شود. پس **کد برنامه در این مرحله اجرا نمی‌شود** و هر تغییری در `providers.ts` این را عوض نمی‌کند.

۳. **این سرویس‌دهنده است، نه DNS و نه فایروال محلی:**
   - `resolv.conf` = `185.192.112.100, 185.192.113.100` (Radcom، ایران)
   - هیچ تونل/TUN، هیچ پروسهٔ VPN، هیچ پروکسی، هیچ قاعدهٔ redirect
   - `iptables` با دسترسی root خوانده نشد، ولی هیچ نشانهٔ دیگری نیست

۴. **فیلتر مخصوص مقصد است، نه کل شبکه.** از همین هاست در همان لحظه: `npm registry` و `api.github.com` جواب می‌دهند، ولی کایا timeout می‌شود. پس «بسته‌ها قبل از رسیدن دور ریخته می‌شوند» غلط است و نباید دنبال DNS/فایروال رفت.

۵. **IP خروجی با IP سرور یکی نیست:**
   - IP عمومی که سرور می‌بیند: `51.81.168.118` (**OVH، آمریکا**)
   - `icanhazip.com` گاهی `185.192.112.49` (ایران) می‌دهد → یعنی خروجی بسته به مقصد متفاوت است
   - روی کارت شبکهٔ سرور فقط یک آدرس غیرلوکال وجود دارد و همان هم آدرس عمومی ایران نیست
   - یعنی NAT بالادست ترافیک را از مسیر خارجی بیرون می‌برد

۶. **TLS واقعی است** (`Google Trust Services`, `Sectigo`) ⇒ MITM نیست.

### آنچه در کد فعلی ساخته شده و باید حفظ شود

- `lib/server/kaya-egress.ts` — انتخاب آدرس مبدأ سوکت برای درخواست کایا (فقط کایا، نه ترافیک دیگر). **نکتهٔ مهم:** `undici` گزینهٔ `connect.localAddress` را نادیده می‌گیرد؛ باید `buildConnector` را wrap کرد. این تست شده و در `tests/kaya-egress.test.ts` پین شده است.
- `lib/server/kaya-egress-store.ts` + `app/api/admin/kaya-egress/route.ts` + فیلد «آدرس خروجی برای کایا» در `components/api-connection.tsx`
- `lib/server/kaya-probe-readings.ts` — تبدیل پاسخ کایا به جملهٔ لایه‌محور (۴۰۱ = کلید، بی‌پاسخ = مسیر)
- `scripts/nomreh-kaya-test.cjs` — تست واقعی با کلید واقعی؛ روی Node 17 خودش را روی Node 22 محلی دوباره اجرا می‌کند (`scripts/lib/plesk-node-delegate.cjs`)
- `scripts/nomreh-kaya-test-selftest.cjs` — ۱۱ بررسی بدون شبکه، روی یک کایای تقلبی
- `npm run kaya:measure` — اندازهٔ بدنهٔ درخواست در برابر سقف ۲۴ مگابایتی کایا
- `docs/kaya-block-diagnosis-fa.md` — خلاصهٔ تشخیص

### محدودیت‌های غیرقابل‌مذاکره

- **مستقیم.** بدون relay، بدون worker روی GitHub، بدون تونل، بدون V2Ray، بدون Shecan برای کایا.
- **هرگز مدل را خودکار عوض نکن.** مدلی که ادمین انتخاب کرده باید همان باشد.
- **خطاهای پنل معلم نباید جزئیات فنی داشته باشد** (نه نام مدل، نه نام سرویس‌دهنده).
- **حداکثر ۱۲۰ درخواست در هر ۲۰ دقیقه** به هر مقصد؛ سقف سخت. counter آن باید در `/admin` دیده شود.
- **هرگز نگو «درست شد» تا وقتی خودت اجرا و تأیید نکرده‌ای.**
- تغییرات جراحی و با پشتیبان؛ کد کاربر را نشکن.
- کاربر **shell ندارد**؛ فقط کنسول `npm` در Plesk که **همه را با `npm` پیشوند می‌کند** و فقط `npm run <script>` را می‌فهمد. Node کنسول **17** است (بدون `fetch`، بدون `?.`، بدون `??=`).
- پاسخ‌ها **فارسی**.
- **فایل zip جدید نفرست** مگر کاربر بخواهد؛ اول تشخیص، بعد یک بستهٔ نهایی.
- **پاسخ کوتاه.** کاربر از حجم توضیح و نسخه‌های پشت‌سرهم کلافه شده است.

### کاری که باید بکنی (به همین ترتیب)

**گام ۱ — کشف «آدرسی که کایا قبول می‌کند»، بدون حدس.**
از کاربر بخواه در Plesk این سه مقدار را ببیند (هر سه در `/admin` → «تشخیص شبکه» هست):
- `IP عمومی خروجی`
- فهرست «آدرس‌های روی این سرور»
- خروجی `npm run kaya:egress -- --test` (نسخهٔ v22+ این دستور را دارد)

سپس تعیین کن آیا آدرسی روی همان ماشین وجود دارد که کایا قبولش کند. اگر آدرس ایرانی روی کارت شبکه نیست، **این را صریح بگو**: bind کردن آدرس عمومی‌ای که روی ماشین نیست ممکن نیست (`EADDRNOTAVAIL`)، و این تنها جایی است که کد نمی‌تواند کمکی کند.

**گام ۲ — اگر آدرس روی ماشین هست:** در فیلد «آدرس خروجی برای کایا» بگذار و با «آزمون واقعی کایا» تأیید کن. تا سبز نشد، چیزی نساز.

**گام ۳ — اگر آدرس روی ماشین نیست، دو راه مستقیم باقی است و هر دو باید به کاربر گفته شود، نه انتخاب خودت:**
- (الف) از هاستینگ بخواه آدرس ایرانی را به‌صورت secondary روی interface بگذارد؛ متن درخواست آماده در `docs/kaya-block-diagnosis-fa.md` هست.
- (ب) تغییر سرویس‌دهنده به یکی که از IP فعلی (آمریکا) جواب می‌دهد. **این را با شواهد بگو، نه با حدس:** کایا از IP آمریکا ۲۰۰ می‌دهد؛ Gemini با کلید معتبر از IP آمریکا هم کار می‌کند (تحریم ایران به IP غیرایرانی کاری ندارد).

**گام ۴ — فقط وقتی مسیر باز شد:** بستهٔ نهایی با تست‌های `npm test` و `npm run build` سبز، و **بعد** بگو کار می‌کند که خروجی موفق را دیده باشی.

### چیزی که هدر رفته و تکرارش نکن

- تست کردن دوبارهٔ DNS/TLS/TCP به‌عنوان «شاید این بار» — نتیجه در ۶ ساعت گذشته ثابت بوده.
- `traceroute -T` (اجازه ندارد)، `iptables` (root ندارد).
- فرض «تحریم کایا برای IP خارجی» — رد شده، کایا به IP آمریکا جواب می‌دهد.
- فرض «همهٔ خروجی OVH است» — رد شده، بستگی به مقصد دارد.
- ساختن قابلیت مانیتور/نگهبان — کاربر صریحاً نمی‌خواهد.
- فرستادن zip تازه برای هر تغییر کوچک.

### تعریف موفقیت

یک بار تصحیح واقعی روی هاست، با کایا، بدون هیچ واسطه‌ای، که خروجی موفقش را دیده باشیم. نه کمتر.
